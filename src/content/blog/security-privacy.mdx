> **TLDR:** When a shell-capable agent can answer a group chat, security depends on more than approval prompts. Hermes documents eight layers, from deciding who may talk to the agent to isolating sessions and sanitizing terminal input. Configure the flexible controls to fit your operation, but remember the invariant: no approval mode, YOLO setting, or user approval bypasses the hardline blocklist.

## The eight-layer security model

This refresh keeps the guide’s original job: a practical tour of Hermes Agent security and privacy configuration. It rechecks the existing approval, file-write, and network guidance and covers additional documented controls, including context-file scanning, content-level command checks, approval responders, and the supervised-gateway guard.

The official [Hermes security guide](https://hermes-agent.nousresearch.com/docs/user-guide/security) organizes security into eight layers:

1. **User authorization:** who can talk to the agent.
2. **Dangerous-command approval:** human review for risky operations.
3. **File-write safety:** a denylist and optional sandbox for `write_file` and `patch`.
4. **Container isolation:** sandboxing with hardened settings.
5. **MCP credential filtering:** limiting environment variables passed to MCP subprocesses.
6. **Context-file scanning:** detecting prompt injection in project files.
7. **Cross-session isolation:** keeping session data separate and hardening cron storage paths.
8. **Input sanitization:** validating terminal working-directory parameters against an allowlist to prevent shell injection.

The rest of the guide follows these layers, with the hardline blocklist as the essential floor beneath configurable approval choices.

## Layer 1: Who may talk to the agent

### Gateway authorization

The gateway’s `_is_user_authorized()` check follows this order: a per-platform allow-all flag; the DM pairing approved list; platform-specific allowlists such as `TELEGRAM_ALLOWED_USERS`; the global `GATEWAY_ALLOWED_USERS` list; global `GATEWAY_ALLOW_ALL_USERS`; and, finally, deny by default.

That last step matters: **if no allowlists are configured and `GATEWAY_ALLOW_ALL_USERS` is not set, all users are denied**. Platform settings can also have configuration equivalents; an explicit environment variable takes precedence. Review the [gateway authorization details](https://hermes-agent.nousresearch.com/docs/user-guide/security) before opening access to a group or platform.

### DM pairing

Pairing lets you approve an unauthorized direct-message user without making the platform open to everyone. Hermes issues an eight-character pairing code. Approve it with:

```bash
hermes pairing approve <platform> <code>
```

Codes expire after one hour. The documented safeguards include one request per user every ten minutes, a maximum of three pending codes per platform, and a one-hour lockout after five failed approval attempts. Pairing data files are permission-restricted, and codes are not logged to stdout.

There is a Docker footgun: run the approval command as the `hermes` user, not root. Root-created approvals are silently ignored:

```bash
docker exec -u hermes hermes-agent hermes pairing approve <platform> <code>
```

## Layer 2: Approval modes

The configurable `approvals.mode` controls dangerous-command approval. The default is `smart`; the modes and scoped settings are described in the [approval-mode documentation](https://hermes-agent.nousresearch.com/docs/user-guide/security#approval-modes).

| Mode | Behaviour | Who answers | Bypasses the hardline blocklist? |
|---|---|---|---|
| `smart` (default) | An auxiliary LLM auto-approves low-risk commands “for that command only,” auto-denies genuinely dangerous ones, and escalates uncertain cases. Certain `osascript` classes always prompt. | Operator at the CLI prompt or chat card when escalated. | **No** |
| `manual` | Always prompts for dangerous commands. | Human at the CLI or in chat. | **No** |
| `off` | Disables all approval checks; equivalent to running with `--yolo`. Skips the `trust: untrusted` MCP write prompt, but a declared MCP spend limit still asks. | Nobody; no approval prompt. | **No** |
| YOLO (`--yolo`, `/yolo`, or `HERMES_YOLO_MODE=1`) | Bypasses dangerous-command approval for the current session. `/yolo` applies to that chat; `--yolo` or the environment setting applies to the process’s sessions. | Nobody for bypassed prompts. | **No** |
| Scoped `deny` | Blocks instantly in cron, single-query, or unattended contexts; the agent must find another path. | n/a | **No** |
| Scoped `approve` | Auto-approves in that context, but the hardline floor trips before the approval layer sees the command. | n/a | **No** |

The CLI approval choices are `[o]nce | [s]ession | [a]lways | [d]eny`, with deny as the default. Gateway replies accept yes/approval words or no/denial words, and `HERMES_EXEC_ASK=1` is automatically set when running the gateway.

**Timeout:** `approvals.timeout` defaults to `300` seconds. It fails closed: the command is denied. A timeout is not counted as a denial, which matters for the denial circuit breaker below.

### How `smart` decides

`smart` uses an auxiliary LLM to assess risk. A low-risk command can be approved for that command only; genuinely dangerous commands are auto-denied; uncertain cases go to a manual prompt. Some `osascript` commands always prompt, including scripts that can close a document without saving, quit an app, delete files, send keystrokes, or run `do shell script`, as well as scripts whose contents are not visible on the command line.

You can add free-text guidance with `approvals.smart_policy`. The text is appended to the guardian LLM’s system prompt, the trusted channel. No default value is specified:

```yaml
approvals:
  smart_policy: "Require a human prompt before commands that change production data."
```

### Scoped modes and non-interactive sessions

`approvals.cron_mode`, `approvals.single_query_mode`, and `approvals.unattended_mode` accept `deny` or `approve`; each defaults to `deny`. `unattended_mode` covers webhook, `msgraph_webhook`, and `api_server` sessions. An API-server client that can answer the approval card still receives the request: this includes `/v1/runs` and streaming chat completions, through `POST /v1/runs/{id}/approval`.

## The hardline floor: what nothing gets under

The hardline blocklist is not an approval preference. It is an absolute floor: **nothing bypasses it—not YOLO, `approvals.mode: off`, scoped `approve`, or user approval. There is no override flag.** Scoped `approve` trips after the hardline check, before the approval layer even sees the command. See the [hardline blocklist documentation](https://hermes-agent.nousresearch.com/docs/user-guide/security#hardline-blocklist-always-on-floor).

Examples include `rm -rf /` variants, the fork bomb `:(){ :|:& };:`, `dd if=/dev/zero of=/dev/sd*`, `rd /s /q C:\`, and `Restart-Computer`. Some superficially related commands remain approvable: `Clear-Disk -WhatIf` is a preview, and a literal `-Include *.tmp` filter is a constrained selection. If quoting cannot be parsed safely, Hermes fails closed with a `malformed executable payload` error.

### Content-level command checks

Some command checks examine the content being sent, not just the executable. A `curl` or `wget` request body carrying a secret is flagged—for example, `-d "k=$OPENAI_API_KEY"`, `-F file=@.env`, `-T ~/.ssh/id_rsa`, or `--post-file=/etc/passwd`. An `Authorization` header used for ordinary API access is not flagged.

Invisible or bidirectional Unicode control characters are also flagged. Emoji joiners, keycap emoji, and presentation selectors are exceptions. Both checks use the normal approval flow, like other dangerous patterns. They do not create a route around the hardline blocklist. Details are in [content-level command checks](https://hermes-agent.nousresearch.com/docs/user-guide/security#content-level-command-checks).

## Deny rules, allowlists, and the approval suggester

### `approvals.deny`

Use `approvals.deny` for configurable command rules that block matches unconditionally. It uses case-insensitive fnmatch globs against the whole command text and individual executable-command candidates. Rules are checked before `--yolo`, `/yolo`, or `approvals.mode: off` are consulted. Changes take effect immediately through the mtime-keyed config cache.

Always quote patterns: a bare leading `*` is a YAML alias and fails to parse. For example:

```yaml
approvals:
  deny:
    - "mkfs *"
    - "curl * | sh"
    - "* --delete-all"
```

A denied command returns a `BLOCKED` error telling the agent not to retry or rephrase. Deny rules apply across terminal backends, including isolated containers, but they are a shell-command policy—not a complete shell interpreter or an OS capability sandbox. Read the [deny-rule details](https://hermes-agent.nousresearch.com/docs/user-guide/security#user-defined-deny-rules-approvalsdeny) and adapt patterns to the commands you actually need to block.

### Top-level `command_allowlist` and suggestions

The permanent allowlist is the top-level `command_allowlist`, **not** an `approvals:` setting. Entries can be exact command text, a shell-style glob such as `podman *`, or a dangerous-pattern rule key. These entries are honored on every surface, including unattended ones. Removing an entry requires a restart.

Before writing an allowlist by hand, consider `hermes approvals suggest`. It scans `~/.hermes/state.db`; the documented `--days` default is `90`, and `--min-count` defaults to `2`. You can inspect proposals, select them with `--apply 1,3`, or request `--json` output. Nothing is ever applied automatically, and destructive classes are never proposed. See [approval-history suggestions](https://hermes-agent.nousresearch.com/docs/user-guide/security#mining-approval-history-hermes-approvals-suggest).

### The denial circuit breaker

`approvals.denial_breaker_threshold` defaults to `3`. After that many consecutive denials in a session, the denial message escalates to a hard-stop instruction: stop, report the blocked operation, and ask you to run it manually or use `/approve`. Any approval resets the count; setting the threshold to `0` disables the breaker.

## Who may answer an approval

`approvals.approvers` defaults to `["*"]`, meaning any admitted member may answer a pending approval. To narrow the audience, list specific member IDs in `approvals.approvers`; who counts as a platform admin comes from `allow_admin_from` for DMs and `group_allow_admin_from` for groups. Under the wildcard setting, Discord relay members can answer by button or command only after the relay has delivered one of their messages to the gateway since it last started. Matrix has its own stricter `MATRIX_APPROVAL_REQUIRE_SENDER`, which defaults to on; QQBot accepts clicks only from the session’s own user. Picker cards and `/update` belong to the member who opened them. See [approval responders](https://hermes-agent.nousresearch.com/docs/user-guide/security#who-can-answer-an-approval-in-a-shared-chat-approvalsapprovers).

## Layer 3: File-write safety

### Denylist and optional sandbox

Hermes checks `write_file` and `patch` against a denylist and optional sandbox. A blocked write **returns an error to the agent immediately—there is no approval prompt and no way to override it from the chat UI**. Examples include:

```text
Write denied: '...' is outside HERMES_WRITE_SAFE_ROOT (...)
Write denied: '...' is a protected system/credential file.
```

Write guards apply to `write_file` and `patch` only, except Windows NT/device-namespace paths, which are also enforced on `read_file`, `search_files`, `@file:`, `@folder:`, and the ACP file bridge. `display.file_mutation_verifier` is on by default. See [file-write safety](https://hermes-agent.nousresearch.com/docs/user-guide/security#protected-paths-always-blocked).

### Optional hard boundary: `HERMES_WRITE_SAFE_ROOT`

Set `HERMES_WRITE_SAFE_ROOT` to one or more allowed roots, separated by `:` on Unix or `;` on Windows. The official Docker image sets it to `/opt/data`. Anything outside the configured root is hard-blocked, not sent through approval; sensitive paths inside the root remain blocked. When unset, writes are unrestricted by this root check, subject to the denylist.

Do not add this setting casually to `~/.hermes/.env`: the agent may then be unable to write its cron jobs or profile skills. This is an absolute write boundary, not a configurable approval rule. The [write-safe-root documentation](https://hermes-agent.nousresearch.com/docs/user-guide/security#hermes_write_safe_root-optional-sandbox) explains its scope.

### Protected paths

Protected paths include OS credential stores such as `~/.ssh/`, `~/.aws/`, `~/.kube/`, `/etc/sudoers`, and `~/.netrc`, plus Hermes secret stores under the active profile, every profile under `profiles/`, and the global Hermes root. `~/.ssh/config` is an exception: it is approval-gated rather than hard-blocked; non-interactive callers fail closed.

`.env`, `.env.local`, `.env.production`, and `.envrc` are read-denied anywhere on disk but remain writable. Hermes control files such as `auth.json`, `config.yaml`, and `webhook_subscriptions.json` are also read-denied but writable.

Windows NT/device-namespace paths such as `\??\...`, `\\.\...`, `\\?\UNC\...`, and `\\?\GLOBALROOT...` are rejected for reads and writes on every platform. `\\?\C:\...` and `\\server\share` are unaffected.

## Layers 4 and 8: Container isolation and terminal hygiene

Hermes documents these Docker `_BASE_SECURITY_ARGS`:

```text
--cap-drop ALL
--cap-add DAC_OVERRIDE
--cap-add CHOWN
--cap-add FOWNER
--security-opt no-new-privileges
--pids-limit 256
--tmpfs /tmp:rw,nosuid,size=512m
--tmpfs /var/tmp:rw,noexec,nosuid,size=256m
```

`SETUID` and `SETGID` are added conditionally, not included in the base list. The `/run` tmpfs is hardened with `noexec` by default. Documented resource settings include `container_memory: 5120`, `container_disk: 51200`, `container_persistent: true`, and `docker_forward_env: []`; the last is an explicit allowlist, not a pass-through of the host environment. Persistent Docker sandboxes bind-mount `/workspace` and `/root` from `~/.hermes/sandboxes/docker/<task_id>/`; ephemeral mode uses tmpfs. Review the [Docker security flags](https://hermes-agent.nousresearch.com/docs/user-guide/security#docker-security-flags) before choosing a backend.

Dangerous-command checks run on `local` and `ssh` backends. They are skipped for container backends—including Docker, Singularity, Sprites, Modal, Daytona, and Vercel Sandbox—because the container is the boundary. Do not treat container isolation as though the same dangerous-command checks ran inside it.

Layer 8 has one documented description: terminal working-directory parameters are validated against an allowlist to prevent shell injection. Checklist: set `terminal.cwd` thoughtfully; no further behavior is assumed here.

## Layer 5: Secrets leaving the conversation

### MCP credential filtering

MCP subprocesses receive a limited safe environment: `PATH, HOME, USER, LANG, LC_ALL, TERM, SHELL, TMPDIR`, plus `XDG_*` variables. Hermes-managed credentials—including model-provider keys, tool keys used by Hermes, and bot, gateway, and relay tokens—are held back. Explicit `mcp_servers.<name>.env` entries pass through.

Credential-shaped values in MCP errors are replaced with `[REDACTED]`, including GitHub PATs such as `ghp_...`, OpenAI-style keys such as `sk-...`, Bearer tokens, and `token=`, `key=`, `API_KEY=`, `password=`, or `secret=` parameters.

### Secret and phone-number redaction

`security.redact_secrets` defaults to `true`. It redacts patterns resembling API keys, tokens, and passwords in tool output before they enter conversation context and logs. Reads of credential-bearing files can mask credential-shaped assignments with the non-reusable marker `«redacted-secret»`. Ordinary source and project configuration files keep only vendor-prefix matching, so a value like `MAX_TOKENS: 100` is not treated as a secret.

`security.redact_phone_numbers` also defaults to `true`, but its scope is specific: it masks E.164 numbers in replies and everything the gateway sends to chat platforms, even if `redact_secrets` is false. It does not describe broader personal-information redaction. The [configuration guide](https://hermes-agent.nousresearch.com/docs/user-guide/configuration) shows these settings.

## Network egress: SSRF protection and website blocklist

### Private-address protection

Web fetches and other covered URL surfaces block private and special addresses, including RFC 1918 ranges, loopback, link-local `169.254.0.0/16` (including cloud metadata at `169.254.169.254`), CGNAT `100.64.0.0/10`, cloud-metadata hostnames, and reserved, multicast, or unspecified addresses. DNS failures are blocked, and redirect chains are revalidated at each hop. See [SSRF protection](https://hermes-agent.nousresearch.com/docs/user-guide/security#ssrf-protection).

`security.allow_private_urls` defaults to `false`. Setting it to `true` lifts the RFC 1918, loopback, link-local, and CGNAT checks for covered tools; cloud-metadata endpoints and the host-substring guard remain blocked. Terminal opens are not URL-guarded. `security.fake_ip_ranges` is empty by default; overlapping protected ranges are ignored with a warning.

```yaml
security:
  allow_private_urls: false
  fake_ip_ranges: []
```

### Configurable website blocklist

The website blocklist is a separate, configurable domain policy. Its keys are `enabled`, `domains`, and `shared_files`; `enabled` defaults to `false`. Patterns can name an exact domain, a wildcard subdomain such as `*.internal.company.com`, or a TLD wildcard such as `*.local`.

```yaml
security:
  website_blocklist:
    enabled: true
    domains:
      - "admin.example.com"
      - "*.internal.company.com"
    shared_files: []
```

When enabled, it applies to `web_extract`, browser navigation, `vision_analyze` and `video_analyze` URLs, and skills-hub downloads. `web_search` is not gated. The policy is cached for 30 seconds; a blocked URL returns an error explaining that the domain is blocked by policy. See the [website blocklist configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#website-blocklist).

## Layer 6: Context-file injection protection

Hermes scans context files for instructions to ignore prior instructions, suspicious hidden HTML comments, attempts to read secrets, credential exfiltration through `curl`, and invisible Unicode characters. A blocked `AGENTS.md` can produce:

```text
[BLOCKED: AGENTS.md contained potential prompt injection (prompt_injection). Content not loaded.]
```

An operator’s own `SOUL.md` in `HERMES_HOME` loads with a warning. A `SOUL.md` owned by `distribution.yaml` and installed through `hermes profile install <git-url>` or `hermes profile update` does not receive that exception. See [context-file injection protection](https://hermes-agent.nousresearch.com/docs/user-guide/security#context-file-injection-protection).

## Layer 7: Cross-session state and hardening checklist

Cron storage paths are hardened against path traversal, but do not ask the agent to patch `~/.hermes/cron/jobs.json` directly. Use `cronjob_manage`, `hermes cron`, or `/cron`.

The supervised-gateway lifecycle guard is a separate absolute restriction. It prevents a supervised process from stopping or restarting its own gateway; user approval, YOLO, and `force=True` do not bypass it. Image-name kills such as `pkill -f python` or `taskkill /F /IM python.exe` are refused, while scoped commands such as `kill <pid>` pass. The guard is active under systemd, launchd, s6, and Windows Scheduled Task launchers through the `HERMES_SUPERVISED_CHILD` marker. Details are in the [supervised-gateway restriction](https://hermes-agent.nousresearch.com/docs/user-guide/security#supervised-gateway-lifecycle-restriction).

Before relying on the setup, review this operator checklist:

- Decide who may contact the gateway; do not assume an empty allowlist means open access.
- Choose approval modes and scoped behavior deliberately; keep the hardline floor in view.
- Review quoted `approvals.deny` patterns, then inspect suggestions before applying allowlist entries.
- Restrict `approvals.approvers` where any admitted group member should not answer.
- Set a write-safe root only when its effect on cron jobs and profile skills is understood.
- Check container resource and environment settings, and remember which backends skip dangerous-command checks.
- Confirm private-URL and website-blocklist policies match your intended network access.
- Keep `approvals.mcp_reload_confirm` and `approvals.destructive_slash_confirm` at their documented default of `true` unless you have a reason to change them. `HERMES_TUI_NO_CONFIRM=1` force-skips the destructive-slash confirmation modal.
- Do not rely on `security.tirith_*`: those settings were removed and enable nothing in their place.

## FAQ

### Does YOLO disable the hardline blocklist?

No. Neither YOLO, `approvals.mode: off`, scoped `approve`, nor user approval bypasses the hardline blocklist.

### Can I approve a protected file write in chat?

No. A blocked write returns an error immediately; there is no approval prompt or chat-UI override. The `~/.ssh/config` exception is approval-gated, not hard-blocked.

### Does `approvals.deny` require a restart after edits?

No. Its mtime-keyed configuration cache makes changes take effect immediately. Removing a top-level `command_allowlist` entry, by contrast, requires a restart.

### Does the website blocklist block web search?

No. The documented blocklist applies to specific fetch, browser, analysis, and skills-hub surfaces; `web_search` is not gated.

### Does phone redaction cover every phone-number format?

No. The documented behavior masks E.164 phone numbers in replies and gateway messages to chat platforms.
